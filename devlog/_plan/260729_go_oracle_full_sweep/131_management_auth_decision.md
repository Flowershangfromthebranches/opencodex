# 131 — 관리/데이터 자격증명 분리: 사람 결정이 필요한 지점

`130_platform_hardening.md`의 1순위 항목이다. 측정은 끝났고, **구현 방향에 owner 결정이
필요하다.** 이 문서는 그 결정을 위한 사실 정리다.

## 사실

### 오라클의 구조

관리 API는 데이터 플레인과 **완전히 다른 자격증명**을 쓴다.

| 층 | 자격증명 | 위치 |
| --- | --- | --- |
| 데이터 플레인 (`/v1/*`) | `apiKeys[]`, `authToken` | `auth-cors.ts:214` `isDataPlaneAdmissionSecret` |
| 관리 API (`/api/*`) | admin 토큰 (`ocx_admin_...`) | `management-auth.ts:187` `requireManagementAuth` |
| GUI | 세션 토큰 + CSRF + Origin | `management-auth.ts:160` `issueGuiSession` |

admin 토큰은 `OPENCODEX_ADMIN_AUTH_TOKEN` 또는 `~/.opencodex/admin-api-token`
(0700 디렉터리, 심볼릭 링크 거부, 512바이트 상한, 형식 `^ocx_admin_[A-Za-z0-9_-]{43}$`)에서
온다(`admin-secrets.ts`). 토큰이 없으면 관리 API는 **503**이다 — 열리지 않는다.

GUI 세션은 5분 TTL, 128개 상한이고, 안전하지 않은 메서드는 Origin 일치 + CSRF 토큰을
요구한다(`management-auth.ts:196-213`).

### go의 현재 상태

관리 API가 데이터 플레인과 **같은 admission 경로**를 쓴다(`middleware.go:60-87`). 즉
`apiKeys[]`의 데이터 키로 `/api/*` 전체에 접근할 수 있다. `Authorize` 훅이 있지만
(`server.go:54-56`) 옵션이고 서버 구성에서 주입되지 않는다.

admin 토큰 개념, GUI 세션, CSRF 모두 go에 없다.

**영향 범위**: 관리 API는 provider 설정 쓰기, OAuth 계정 조작, 런타임 재시작,
저장소 정리를 포함한다. 데이터 플레인 키 하나로 그 전부에 닿는다.

## 왜 자율 구현을 멈췄나

이 변경은 **잠금 위험**이 있다. 오라클 의미론을 그대로 옮기면:

- admin 토큰이 없는 상태에서 관리 API가 **503**이 된다.
- 기존 사용자의 대시보드는 데이터 키로 인증하고 있으므로 **모두 401**이 된다.
- go 런타임은 GUI 세션 발급 경로가 없으므로, 그것까지 함께 만들지 않으면 대시보드가
  아예 로그인할 수 없다.

즉 "보안 경계를 오라클과 맞춘다"는 곧 "현재 동작하는 모든 대시보드를 끊는다"이다. 마이그레이션
경로 없이 넣을 수 있는 종류의 변경이 아니고, 어느 쪽을 택할지는 코드가 답할 수 없다.

## 선택지

### A. 전체 이식 + 자동 부트스트랩 (오라클 파리티)

admin 토큰 파일을 **첫 실행에 자동 생성**하고, GUI 세션·CSRF까지 이식한다.

- 장점: 오라클과 같은 보안 경계. 데이터 키로 관리 API에 닿지 못한다.
- 단점: 가장 큰 작업(오라클 기준 216 + 25줄 + GUI 세션 발급 경로 + 대시보드 연동).
  헤드리스/스크립트 사용자가 토큰 파일을 읽도록 문서를 바꿔야 한다.

### B. 분리하되 loopback 기본 허용 (점진)

admin 토큰을 도입하되, **loopback 바인드에서는 기존 데이터 키도 당분간 허용**하고
원격 바인드에서만 강제한다. 경고를 남긴다.

- 장점: 기존 대시보드가 계속 동작한다. 원격 노출 시나리오(가장 위험한 쪽)는 즉시 닫힌다.
- 단점: loopback에서는 경계가 여전히 없다. 로컬 악성 프로세스는 막지 못한다.

### C. 이번 사이클에서는 문서화만

측정 결과를 기록하고 구현은 별도 결정으로 넘긴다.

- 장점: 잘못된 잠금을 만들지 않는다.
- 단점: 가장 큰 보안 간극이 열린 채 남는다.

## 권고

**B.** 이유는 위협 모델의 비대칭이다. 원격 바인드에서 데이터 키로 관리 API에 닿는 것은
자격증명 탈취로 직결되지만, loopback에서는 이미 같은 사용자 권한의 프로세스가 config 파일을
직접 읽을 수 있다 — 그 경우 관리 API 경계는 방어선이 아니다.

B는 실제 위험을 닫으면서 기존 사용자를 끊지 않고, A로 가는 길을 막지도 않는다.
